# ChargeTweaks 客户端崩溃排查记录

一次出bug的排查记录，希望可以给你一些启发

> 事件日期：2026-11-14
> 涉及版本：v1.0.0（出问题） → v1.1.0（修复并验证稳定）
> 线上结果：**修复后 13 机器人 + 1 真人 场景稳定运行，未再复现**
> 相关文档：[../README.md](../README.md) · [./实现原理与开发记录.md](./实现原理与开发记录.md) · [../../1服务器开服教程/服务器参数手册.md](../../1服务器开服教程/服务器参数手册.md)

## 1. 摘要（TL;DR）

**现象**：服务端模组部署后，玩家游玩一段时间客户端崩溃；服务端本身不崩。

**复现矩阵（实测）**：

| 场景 | 结果 |
|---|---|
| 不加载 mod | 长时间稳定 |
| mod + 5 机器人 + 1 真人 | 长时间稳定 |
| mod + 13 机器人 + 1 真人 | 约 5 分钟客户端崩溃 |

**根因（两层）**：

1. **客户端引擎缺陷（直接原因）**：`TaleWorlds.Native.dll` 在处理网络消息时对「已不存在的 agent」解引用空指针 —— `movzx ecx, word ptr [rax+5AAh]`，其中 `rax` 取的子对象为 `NULL`。
2. **agent 索引失步（触发条件）**：服务器先让客户端删除 12 号 agent，之后 5 秒内仍持续向客户端下发 12 号的状态/击杀消息，客户端找不到该 agent，最后一条 `agent_killed` 之后立刻崩溃。

**模组的关系**：模组代码不在崩溃现场（客户端根本没加载它），但它把「马撞人」放大 20 倍，让 **AI 骑兵互相冲撞也变成一击必杀**，把 bot 的击杀/重生/删除事件密度抬高一个量级，从而大幅提高撞上该引擎竞态的概率。

**修复思路**：不改游戏行为正确性，只**降低事件密度**——默认只放大玩家骑手、AI 骑兵保持原版，并给每秒放大次数设上限。

**结果**：v1.1.0 上线后稳定运行。

---

## 2. 现象与背景

- 模组：服务端专用（`ModuleCategory = Server`），功能是把「骑马冲撞」的最终伤害乘以可配置倍率（默认 20）。
- 客户端不需要安装该模组，也不会出现模块不匹配。
- 崩溃全部发生在**客户端**；服务端进程未崩溃、自动重启脚本未触发。
- 客户端画质被压到最低（`number_of_ragdolls=0`、`particle_quality=0` 等），与本次问题无关，但复现测试时保持一致。

## 3. 崩溃取证（dump 解析）

崩溃包内容：`help/crashes/2026-11-14_10.47.11/`（`dump.dmp` 686 MB + `crash_tags.txt` + `watchdog_log_8888.txt` + `rgl_log_8888.txt` + `module_list.txt`）。
dump 通过解析 minidump 的**异常流 / 模块表 / 内存映射 / 线程栈**逐层还原。

### 3.1 崩溃事实

| 项 | 值 |
|---|---|
| 崩溃时间 | 2026-11-14 18:47:01（本地时间） |
| 进程 | Mount & Blade II Bannerlord，`Win64_Shipping_Client`，v1.5.7.125802 |
| 进程运行时长 | 174.9 秒 |
| 异常码 | `0xC0000005`（ACCESS_VIOLATION，**读**：Parameter-0 = 0） |
| 访问地址 | `0x00000000000005AA`（= NULL + 0x5AA） |
| 故障地址 | `0x7FFFB9ABDA47` |
| 所属模块 | `TaleWorlds.Native.dll + 0x5EDA47` |
| 故障指令 | `0F B7 88 AA 05 00 00` → `movzx ecx, word ptr [rax+5AAh]` |
| 前一条指令 | `48 8B 86 F8 08 00 00` → `mov rax,[rsi+8F8h]`，此时 `rax = 0` |
| 寄存器 | `RAX=0`，`RSI=RCX=0x5650F41C1D0`（合法堆指针） |

### 3.2 指令语义

故障点是一段「置位 / 清位」的辅助逻辑：

```asm
mov  rax, [rsi+8F8h]        ; 取某个子对象 → 本次取到 NULL
movzx ecx, word ptr [rax+5AAh]   ; ← 崩溃：读 NULL+0x5AA
test cx, cx
je   ...
or   word ptr [rax+5ACh], cx
```

即：**`this` 本身有效，但 `this->[0x8F8]` 这个子对象是空的**，随后往它身上写标志位。
性质是「对象缺失」，不是数组越界、不是内存踩踏、不是显存/驱动问题。

### 3.3 排除项

| 怀疑方向 | 结论 | 依据 |
|---|---|---|
| 内存不足 / 泄漏 | 排除 | 托管堆 203.9 MB；页面文件 19040 MB 已用 / 15513 MB 仍可用 |
| 显卡 / Shader | 排除 | `d3d11_debug_layer.txt` 为空；崩溃指令与渲染无关 |
| C# 托管异常未捕获 | 排除 | 崩溃点在原生代码；托管异常都被 handler 捕获并记录 |
| 第三方模组冲突 | 排除 | 262 个已加载模块**全部是原版/系统 DLL**，没有 `ChargeTweaks.dll` |

### 3.4 线程

崩溃发生在 239 个线程之一，该线程栈上探到的返回地址**全部落在 `TaleWorlds.Native.dll`**（示例：`+0x724C9F`、`+0x724BE6`、`+0x48C9C`、`+0x5D112E`）。
与日志中 `MPSGE_*` 原生事件处理走原生代码相符；该线程不属于托管线程池。

### 4.4 时间线解读

1. 服务器向客户端发 `delete_agent 12`（网络裁剪 / 尸体清理），客户端把 12 从本地 agent 表移除；
2. 此后服务器仍把 12 号当作「存活、血量 42、在换武器」的 agent 继续下发状态 —— 服务器认为客户端有，客户端其实没有；
3. 服务器最后下发 12 号的 `agent_killed`，客户端查不到对应 agent，原生处理路径没有做空判断 → 在 `[rax+0x5AA]` 处空指针。

**这与 dump 里 `this->[0x8F8] == NULL` 然后写成员的形态完全吻合。**

## 5. 根因分析

### 5.1 直接原因

客户端原生代码在「agent 已不存在」的情况下继续访问其关联子对象，触发空指针解引用。
这是**引擎健壮性缺陷**，不由模组代码产生（客户端未加载模组）。

### 5.2 上层原因

服务端与客户端的 **agent 索引表失步**：
服务器让客户端删除了某个索引，之后又复用该索引或继续引用它，却没有重新下发 `CreateAgent`。
索引复用在高事件密度下非常频繁（本局 68 个索引、94 次创建，29 个索引被创建 ≥2 次）。

### 5.3 为什么模组会放大问题

×20 让所有冲撞（**包括 AI 骑兵互撞**）都变成一击必杀：

- bot 死亡更快 → 重生更快 → `CreateAgent` / `agent_killed` / `delete_agent` / `add_corpse` 更密集；
- 死亡事件越密集，索引复用与网络裁剪的交叉窗口越多；
- 因此撞上 5.2 那个竞态的概率显著上升。

13 bot 局里，额外击杀主要来自 **AI 之间的冲撞**，玩家自己的冲撞只占很小一部分 —— 这正是优化切入点。

### 5.4 为什么不是模组代码的问题

| 证据 | 说明 |
|---|---|
| 崩溃进程模块表 | 262 个模块全为原版，无 `ChargeTweaks.dll` |
| 客户端启动配置 | 联机模块只有 `Native`、`Multiplayer` |
| 崩溃位置 | `TaleWorlds.Native.dll` 原生指令，非托管代码 |
| 模组职责 | 只重写 `ApplyGeneralDamageModifiers` 做一次乘法，不碰网络消息、不碰 agent 生命周期 |

**结论：模组不是崩溃的成因，而是「提高触发概率的负载放大器」。**

## 6. 修复方案 v1.1.0

### 6.1 设计目标

1. 保留「玩家骑马冲撞伤害放大」的核心体验；
2. 把额外产生的击杀/重生事件密度压回接近原版；
3. 所有新行为都可通过配置开关，支持 A/B 验证；
4. 任何非法配置都能安全回退，绝不让服务器启动失败。

### 6.2 改动清单

| 改动 | 默认值 | 作用 |
|---|---|---|
| `PlayerMultiplier` / `BotMultiplier` 拆分 | 20 / **1.0** | AI 骑兵不再被放大，砍掉绝大部分额外击杀 |
| `MaxEmpoweredHitsPerSecond` | **8**（0=不限） | 每秒最多放大 N 次，避免一次冲锋在同一秒刷出大量死亡事件 |
| `AffectFriendlyFire` | **false** | 友伤场景不再放大，减少异常结算 |
| 跳过已死亡 / 未激活目标 | 内置 | 避免对已被移除的 agent 追加伤害 |
| `NaN` / `Infinity` 保护 | 内置 | 异常数值不再流入血量与后续结算 |
| `MaxDamage` | 0（不限） | 可选单次伤害上限 |
| 旧配置 `<Multiplier>` 兼容 | 保持旧语义 | 玩家与 AI 使用同一倍率，不因升级 DLL 突然变样 |

### 6.3 关键实现

**真人 / AI 判定**（`ChargeDamageModel.IsPlayerRiddenMount`）：

- 冲撞时攻击者是「马」，取 `Agent.RiderAgent` 得到骑手；
- 骑手满足 `MissionPeer != null || IsPlayerControlled || !IsAIControlled` 即为真人；
- 取不到骑手时退回 `AttackInformation.IsAttackerPlayer` / `OwningAgentMissionPeer` 兜底。

**每秒放大预算**（`ChargeDamageModel.TryTakeBudget`）：

- 用 `Mission.CurrentTime` 做 1 秒滑动窗口；
- 超预算的冲撞按**原版伤害**结算（不是取消伤害）；
- 换图 / 任务切换自动重置。

### 6.4 配置样例

```xml
<ChargeTweaksConfig>
    <PlayerMultiplier>20.0</PlayerMultiplier>
    <BotMultiplier>1.0</BotMultiplier>
    <AffectFriendlyFire>false</AffectFriendlyFire>
    <MaxEmpoweredHitsPerSecond>8</MaxEmpoweredHitsPerSecond>
    <MaxDamage>0</MaxDamage>
    <LogDamage>false</LogDamage>
</ChargeTweaksConfig>
```

启动日志会打印一行确认生效：

```
[ChargeTweaks] 配置: 玩家倍率=20 AI倍率=1 友伤放大=False 每秒上限=8 伤害上限=0 日志=False | ...\charge_config.xml
```

## 8. 下次遇到崩溃怎么查（可复用流程）

### 8.1 先收集

| 文件 | 位置 | 用途 |
|---|---|---|
| `crash_tags.txt` | `crashes/<时间戳>/` | 进程类型、启动参数、版本、硬件 |
| `dump.dmp` | 同上 | 异常码、故障指令、模块、线程栈 |
| `rgl_log_*.txt` | `logs/` 与 `crashes/<时间戳>/` | 崩溃前的网络消息与异常 |
| `module_list.txt` | `crashes/<时间戳>/` | 判断是否有第三方 DLL |
| `watchdog_log_*.txt` | 同上 | 异常记录、内存统计、dump 生成过程 |
| 服务端日志 | 服务器 `bin\win64_shipping_server\logs\` | 同时间段服务器视角（关键） |

### 8.2 三步判断

1. **这是谁的崩溃？** 看 `crash_tags.txt` 的 `Build Name`（`Client` vs `Server`）与启动参数。
2. **是不是模组的锅？** 看 `module_list.txt` 里有没有模组 DLL；没有就不是模组代码崩的。
3. **崩在哪里？** 用 dump 的异常流拿 `ExceptionAddress`，换算成「模块 + 偏移」，再看故障指令语义。

### 8.3 日志关键字

```
could not be found while reading reference from packet   # agent 引用失步
Invalid encode/decode in Integer_compression_info        # 消息流状态/版式不一致
Exception in handler of                                  # 某条消息处理失败
MPSGE_agent_killed / MPSGE_delete_agent                  # 死亡与删除事件
```

## 9. 经验与后续

### 9.1 经验

1. **服务端模组也会影响客户端稳定性**：它改变不了客户端代码，但会改变「事件产生的节奏」，节奏极端时更容易踩到引擎的并发/生命周期缺陷。
2. **判断责任要先看证据**：崩溃模块 + 已加载模块列表，比"最近装了什么"可靠得多。
3. **测试必须覆盖高负载场景**：5 bot 测不出的问题，13 bot 5 分钟就出。
4. **模组要做"可降级"设计**：倍率、限流、友伤都要能配置，出问题能一小时内切回安全档。
5. **保留现场**：dump + 客户端日志 + 服务端日志三件套，缺一不可。

### 9.2 后续可选

1. 用 `LogDamage` 统计每分钟击杀数，作为"事件密度"基线，观察稳定性趋势；
2. 若未来仍偶发崩溃，优先抓**服务端同一时间段**的 `rgl_log`，确认 `delete_agent` 与 `CreateAgent` 的配对；
3. 该崩溃属引擎缺陷，可带 dump 上报 TaleWorlds；
4. 不建议用 Harmony 去补客户端/引擎逻辑——风险远大于收益。

## 附录 C：术语

| 术语 | 含义 |
|---|---|
| agent | 战场中的实体（玩家角色、bot、马、尸体等都算） |
| agent index | 服务器/客户端用来互相引用的编号，会被回收复用 |
| `MPSGE_*` | 多人任务的「服务器生成原生事件」（死亡、删除、尸体等） |
| culling | 服务器把远处/不可见的 agent 从客户端移除（`delete_agent`） |
| 事件密度 | 单位时间内产生/下发的 agent 生命周期事件数量 |
